# P1 技术要求与 DSH 匹配分析、改造选择清单

日期：2026-09-08
状态：**待用户选择；本文件不是实施授权，也不表示新增能力已完成。**

## 1. 结论

**P1 的目标适合在 DSH 上实现，但应迁移“能力与验收要求”，不应照搬旧控制面架构。** DSH 已有原生执行循环、Goal、独立子会话、计划、Skill、上下文压缩、工具拦截、会话持久化、沙箱及 OTel 出口。建议在这些组件上补齐策略插件、证据和少量交互，不再建设另一套 Agent 引擎。

最值得先做的是：**可执行验收 → 自动检查与返工 → 独立审核 → 上下文交接与长会话稳定性 → 人工介入与结果展示**。完整双时态、广泛污染传播、远程环境及外部遥测可分别选择，不作为基本聊天和文件生成的前置条件。

这里的“这个技术要求”按上一轮上下文指原项目 **P1 / Batch 9–13 的五项架构特性**，包括 2026-08-31 补充的四级门控、上下文预算及三层约定。不是重新启动已暂停的 P0 三引擎联邦任务。

## 2. 五项技术要求的匹配判断

| 原 P1 特性 | DSH 已有基础 | 尚缺什么 | 匹配判断 |
|---|---|---|---|
| AR-1 可执行验收、四级门控 | Goal、续跑驱动、工具/停止扩展点、fresh-context 子 Agent | 冻结验收规格、独立 evaluator、不可混用的验收凭证、跨重启阻断计数、合格产物发布约束 | 扩展点匹配较好，强制验收机制需要新增 |
| AR-2 分层上下文、Skill、压缩 | 私有子会话、原生计划、按需 Skill、TokenMeter、摘要压缩、工具结果裁剪及历史投影 | 项目共享事实的版本、阶段化交接、预算分桶、不可裁剪锚点、压缩探针、Skill 内容固定版本 | 基础复用程度高；不需要重写压缩器和 Skill 系统 |
| AR-3 Effect 2PC、双时态、因果审计 | 追加式会话、执行前 checkpoint、未知工具结果恢复提示 | 业务操作身份、确定性外部对账、受控提交、业务有效时间及查询 | 事件基础匹配；通用外部事务并不匹配，必须缩小承诺边界 |
| AR-4 CDE、OpenInference/OTel | 跨平台本地沙箱及能力声明、遥测插件、OTLP 日志出口 | 环境能力合同映射、脱敏白名单、OpenInference span/属性、门控和上下文指标 | 优先适配原生组件；不是从零建设沙箱或 OTel SDK |
| AR-5 ADR、信任标签、能力矩阵、人工介入 | 原生审批、取消、Goal 暂停/恢复、工具策略和事件 | ADR 的机器约束、标签传播、风险选门控、任务版本绑定的干预、能力证据展示 | 人机入口可复用；治理策略与证据语义需补齐 |

### 会影响选项的原生能力事实

1. **Goal 不等于独立验收。** 原生 Goal 明确没有 independent evaluator；记录完成的调用方仍是权威。恢复会话保留目标，但重新启动后不会自动取得续跑许可。应保留这种防止历史任务突然产生费用的行为。[S1][S2]
2. **Hook 不等于完整四级门控。** Claude Code hook 兼容桥的 Stop 可要求继续，但连续阻断上限尚未实现，`stop_hook_active` 始终为 false；它也不是完整 Claude Code Hook 实现。推荐使用 DSH 原生 `agent/turn-stopping`、`agent/pre-step` 等扩展点，而非依赖兼容桥补齐保证。[S3][S4]
3. **fresh-context 已有，不必再造子 Agent。** `spawn` 创建独立会话，不复制父会话历史，支持输出 Schema、深度和工具过滤；用于调查和审核。`fork` 会继承历史，不能冒充独立审核。[S5]
4. **压缩已具备保护源历史和工具配对的基础。** 缺的是 P1 的明确锚点、分层预算及压缩后质量探针，不是“DSH 没有上下文管理”。原生 `summarize()` 提供子类扩展；能否完整覆盖所有裁剪和提交路径仍须做定向验证。[S6]
5. **Skill 已按需读取，但内容不是任务内固定版本。** 原生每次加载重新读取当前文件，明确没有 body revision 协议；同一任务中两次加载可能读到不同内容。[S7]
6. **DSH 已先持久化工具调用意图，再进入工具执行。** 崩溃后区分未开始和结果未知，不能据此证明外部操作完成或未完成。上游明确不保证 generic exactly-once。[S8][S9]
7. **已有 OTel，但默认上传内容不符合 P1 的最小化要求。** 原生 exporter 默认关闭；开启上传时，未加自定义脱敏规则可包含消息、工具输入输出和完整请求头。其当前实现主要是 OTLP logs，不等于 P1 所需 OpenInference traces。[S10]
8. **已有真实 OS 沙箱，但各平台边界不同。** 本地实现涵盖 macOS Seatbelt、Linux bwrap/Landlock、Windows ACL 等，不能概括为“只有 PTY”，也不能因此声称全部具备网络、CPU、内存隔离。[S11]

### 01–04：四级门控不是四个模型按钮

- **L1**：当前 Agent 自检与修改，只产生“候选完成”。01 提供可运行的检查，02 防止自述完成绕过检查。
- **L2**：03 的独立 evaluator 每轮判断继续、候选完成或停滞。模型判断不是确定性 PASS。
- **L3**：02 在结束/受控发布边界执行确定性检查，失败返工；第 8 次仍失败转 `BLOCKED_INTERVENTION`，**不是强制放行、不是发布成功**。
- **L4**：04 的 fresh-context reviewer 审核冻结规格、差异及证据；发现问题关闭旧验收周期，返工后不能拼接旧凭证。

普通任务不强迫走完四层。01/02 可提供明确的基础预设；完整按风险自动选择由 14 负责。用户选择 03/04 时，界面必须显示额外模型调用和预算，避免隐藏费用。

“独立”指任务身份和上下文隔离，可以使用同一个供应商/同一个模型；不要求为 reviewer 另配 API Key。继续复用当前加密凭据服务，不从旧环境导入凭据。

### 每项最低验收场景

| 编号 | 可执行验收内容 |
|---|---|
| 01 | 指定产生某个 HTML 文件及必要结构；缺文件、损坏结构、证据缺失分别不通过。检查绑定文件 digest，修改产物后旧凭证失效。小说质量等主观要求不能伪装成确定性事实。 |
| 02 | 故意给出不合格产物，观察检查→修改；中途重启再继续，阻断计数不重置。第 8 次失败后停止自动续跑，网页显示待人工，不能成为已验收产物。 |
| 03 | 同一真实任务逐轮评估；没有新进展或预算不足时停止。独立 evaluator 看不到实现 Agent 私有历史；重启保留目标和已用预算，但不自动发起收费调用。 |
| 04 | 植入一个规格违例，审核给出 clause/file/evidence 定位，任务定向返工，旧审核凭证不能用于修改后产物。 |
| 05 | 调查子 Agent 输出来源、摘要和未解决项；畸形/超限 Handoff 不进入执行。检查实际模型输入确认没有直接拷贝全部调查日志。 |
| 06 | 两个任务引用同一已确认项目事实；一个 Agent 私有备注不可被另一 Agent 默认读取。事实更新有版本，不静默改变已接受任务的输入；并发更新可检测冲突。 |
| 07 | 压缩前后运行 recall、artifact trail、continuation、decision 探针，检查目标、文件路径、未解决审核及下一步。故意缺锚点时拒绝投影，不损坏工具调用/结果配对。 |
| 08 | 任务中途编辑 Skill 文件，既有任务不能静默采用新内容；展示加载版本。仅加载 Skill 不显示为执行成功，advisory 不能冒充强制门控。 |
| 09 | 清理后保留冻结目标与待办；旁路问题不改主任务上下文且无写工具；只读回看不修改源事件；修改文件/计划产生新任务版本，不宣称撤销了外部写入。 |
| 10 | 在明确允许的测试工具中制造“已写入但结果未保存”，恢复后先对账。支持幂等键的服务不重复提交；无对账能力则显示结果未知并转人工，不能标未执行或成功。 |
| 11 | 后来获知一个更早生效的事实，按记录时间和业务有效时间分别查询得到正确历史；更正只追加，因果链可回查。 |
| 12 | 对当前机器实测可读写目录、进程及网络能力；要求当前平台不支持的限制时拒绝或要求用户换环境，不把声明当隔离证明。 |
| 13 | 检查实际发出的遥测载荷只含允许字段，不含消息正文、私有推理和原始工具结果；步骤/子 Agent 可关联，exporter 失败不改变验收结果。默认不向外发送。 |
| 14 | 同一类任务稳定选择同一冻结门控模板；写入任务不能通过自然语言降低检查要求；修改已接受任务的规则创建有父引用的新任务版本。 |
| 15 | 把不可信文档中的越权指令带入摘要/交接，标签仍传播；验证文件结构只提升该项声明，不把整份文档自动变可信。 |
| 16 | Web 能查看检查/失败/返工/待人工和实际文件；暂停、取消、补充后状态一致，旧页面动作不能操作新版本任务；刷新后能读历史，CLI 查询同一验收状态。 |

上述是**未来验收要求**，不是本轮测试结果。最终 Agent 场景使用用户明确发起的真实本地或云 API 调用；确定性校验器可做单元测试，但不能用 mock 对话代替端到端验收。

## 4. 需要改写、不能直接移植的原设计

### 4.1 去掉旧控制面的硬依赖

旧规格以 Python/LangGraph、Host v2 `RunEnvelopeV2`、Pin 表和三 Runtime 准入为中心；当前分支以 DSH session 和原生插件为中心。

建议：新增任务规格、验收尝试等**插件事件类型**，以 `session_id + task_id + revision` 及必要 digest 绑定输入和证据。`SessionEventMap` 原生支持插件扩展；记录后按原生 `session/flush` 做持久化屏障。[S8]

- 不另建会话事实库，不增加旧准入链、Python 调度器或 Go sidecar。
- 01/02 内包含最小公共结构：任务版本、规格/证据引用、插件事件回放、功能开关；不另立一个用户看不懂的平台工程。
- 阻断尝试和计数变化应来自一个可一致回放的事件，并在继续/停止前 flush；不把多个 JSON 文件分别写入说成数据库事务。
- 共享上下文或业务对账确需跨会话存储时，只为 06/10 增加明确职责的索引；任何缓存可从权威记录恢复，不能形成第二个会话权威。
- 含新事件的会话必须有读取兼容方案。DSH 对未知的必需事件会拒绝重建，不能把关键门控事件随意标为可忽略。关闭功能只停止新任务使用，保留已有任务的 reader/recovery；不能承诺直接换回旧二进制就无损恢复。
- 新分支验收使用单独的 DSH-P1 标识；不能因为本分支通过就授予旧三引擎 `GO_*` 准入。

### 4.2 将通用 Effect 2PC 改为明确边界内的写入协议

**任意 Bash、MCP、第三方 API 不天然支持两阶段提交，也不能通过补一张日志表实现 exactly-once。**

10 建议先覆盖一种真实需要的工具，例如候选 HTML 文件的 staging→校验→发布，或支持幂等键和查询结果的业务 API。其他工具仍执行原生权限策略；不支持确定性对账的副作用明确标 `unknown` 并转人工。

原生流式输出和工作文件可能在验收前已可见。“发布门控”必须区分：**可见草稿/工作产物**与**正式验收通过的产物**。如果允许通用 shell 写最终目录，不能声称 02 已拦截全部发布。完整发布保证还需要 10 的受控路径与写入边界。

### 4.3 保留原生扩展边界，避免无意维护内核分叉

01–06、08、12–16 优先作为独立 Cordis 插件与最小 Web 扩展。07 的摘要校验可先验证 `summarize()` 扩展，但全部裁剪路径、预算锚点与提交前校验是否充分可接入，必须先做小范围验证。09 的视图/上下文操作也须验证原生入口的实际语义。

如果现有扩展点无法保证关键约束，再给出具体上游补丁及维护成本供用户选择，**本清单不预先授权重写 DSH Loop、替换会话格式或大范围修改 third_party**。

### 4.4 确定性与模型判断分开

可机器证明：文件是否存在、Schema、链接是否有效、测试是否通过、工具顺序、已观察到的受控写入次数。

不能仅凭一次 LLM 审核证明：小说一定优秀、事实绝对正确、模型绝不幻觉。此类条件需要引用证据、明确 rubric、独立评审或人工确认，并标出仍属判断的部分。

## 5. 推荐选择与实施顺序

### 推荐首轮：01、02、03、04、05、07、16

先交付一个用户能感受到的闭环：

> 输入目标和验收要求 → 子 Agent 调查并交接 → 生成实际产物 → 运行检查 → 不通过自动返工 → 独立审核 → 网页展示证据和产物；长会话管理预算，停滞或连续失败转人工。

实施顺序建议：

1. **01 + 16 基础展示**：先让用户输入、看到规格和检查结果；16 的其他状态随对应功能补齐，不画全新工作台。
2. **02**：接通真正的检查、返工、重启回放与人工阻断，先验证不会“说通过就通过”。
3. **03 / 04 / 05**：在冻结的公共事件及接口上分工，分别完成独立评估、审核、交接；本步骤没有恢复旧三模式接力的任务。
4. **07 + 16 联合验收**：验证长任务压缩与前台人工操作，交付可测环境。
5. 用户需要项目复用/技能治理时增加 **06、08、14**；需要可靠业务写入时增加 **10、12**；历史追责、遥测、污染治理分别选择 **11、13、15**；上下文操作增强选 **09**。

如当前首要目标仅是“生成能打开的 HTML 并自动改错”，可先缩为 **01、02、04、16**。这仍不包含通用外部写入事务和无人值守持续 Goal。

不要直接把原 Batch 9–13 的旧日历排期当成本分支工期。先依据选项确认范围，再基于扩展点验证拆 Task、确定可并行边界和交付时间。
