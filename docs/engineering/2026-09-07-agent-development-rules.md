# Agent 开发规范与军规：Must / Must Not

日期：2026-09-07  
依据：代码修复提交、人工验收记录与最新 P0 范围裁决。  
性质：工程规范文档；本次不修改 AGENTS.md、不安装 Hook、不新增权限或自动审计任务。  
基线：已提交修复截至 `0bbdd2b`；正在进行的三线增量不计为已验证结果。

## 一句话结论

**以用户能完成的真实任务为交付单位：共用平台、固定身份、可恢复执行、实际产物、分层验收；不能用源码引入、协议定义或大量测试通过替代功能联通。**

## 1. 规范如何使用

- 内容（管控事项）：说明本条军规管什么，例如“组件引入”；Must 和 Must Not 分别规定该事项必须做到什么、禁止做什么。
- Must：实现或修复触及该行为时必须满足，并提供相应验证。
- Must Not：禁止用表中做法绕过问题或掩盖未完成能力。
- 本文是 advisory 工程约定，不是已经执行的 deterministic Hook。现有测试/运行时约束能够强制的部分以实际代码为准；未实现的规则不宣称已自动保证。
- 每个增量只应用相关规则，不要求每轮重跑全部测试、全仓安全扫描或再次建立签名证明体系。
- 真实验收与开发期测试分开：可控替身用于协议和失败分支；它不能被记为真实模型调用通过。
- 出现协议或范围冲突，记录最小裁决并继续可独立工作；涉及删除、外部发布、秘密或新的用户选择则按既有授权边界处理。

| B06 | 写操作幂等与恢复 | 重复命令返回原结果；已确认写操作不重复执行，未知写结果保留待确认状态。 | 将所有异常标为可重试，或重新执行写文件/外部写入来“证明恢复成功”。 | S09/S14；重复提交、取消和中断恢复核验实体数量与状态，不能只看 completed。 |

## 4. 每次增量的最小开发流程

1. 写明用户本次能多完成哪件事，选出相关军规，不复制全表作为检查负担。
2. 明确修改文件、公共接口生产者/消费者及仍未接通的边界。
3. 先写并运行根因/功能行为测试，确认预期失败，再做最小实现。
4. 定向复测；接口或身份变化增加跨层与旧数据兼容检查。里程碑再集中全量回归。
5. 独立规格与质量审核只审相关改动；问题回给原执行者，不启动重复的审核链。
6. 按文件归属提交可恢复增量，报告实际结果。所有 P0 功能完成后统一真实验收。
7. 需要用户录入时提供 GUI，明确需要输入什么、为什么需要，不索取聊天中的密钥。

## 5. 修复记录模板

每条记录应能回答“什么坏了、为什么、如何证明、有没有伤到旧数据”，而不是只写“已修复”。

```text
问题编号 / 日期：
用户可见症状：
发生阶段：配置 / 准入 / 模型调用 / 工具 / 投影 / 存储 / 前端
已证实根因：
尚未证实的推测：
原失败输入与复现条件（不含秘密）：
最小修改及提交：
关联规则：
RED / GREEN 命令及结果：
涉及旧记录/重试/取消/恢复的验证：
真实 API：已执行 / 未执行；当前构建：
用户可操作入口与步骤：
仍未接通或未验证：
```

## 6. 当前三线立即适用的重点

- Goose / DSH：A01、A02、A04、B04、C04；原生 Session/ToolRuntime 必须接平台，不另建模型配置。
- 公共平台：A03、B01、B02、B05、B06；runtime_id 新字段尤其不能改变旧任务身份。
- 前端与 Artifact：D01–D04；能选择、能执行、能看到真实文件是不同出口，逐个验证。
- 所有执行者：E01–E06；不泄露秘密、不删除用户记录，不把未完成增量包装成整包完成。

本次提炼借助 extract-wisdom 的来源—洞察—行动方法，按用户指定的 Must/Must Not 形式整理；未将资料中无关的通用生活建议、习惯或无证据数量要求加入工程规范。
